# 第2章 MCP核心原理
2.1.	MCP基本功能
MCP是一项专门设计的协议规范，目的是在应用程序（客户端）与语言模型（或其代理服务）之间高效且结构化地传递上下文信息。我们可以把MCP理解为一段高速路，用于连接城市之间的交通线。MCP就是一条连接应用程序（客户端）与语言模型（或其代理服务）之间的“高速路”。MCP的出现是为了解决LLM应用落地过程中“最后一公里”的上下文传递难题而出现的标准化尝试。
MCP的核心目标是解决在与LLM交互是普遍存在的“上下文缺失”问题。MCP通过定义一套标准的组件、交互流程和数据格式，使得应用程序能够系统性收集、组织并提供这些上下文，让LLM如同拥有了“短期记忆”和“环境感知能力”，从而做出更智能、更准确的响应。
MCP可以解决的问题主要涉及以下几个方面：
1.	上下文碎片化
假设你在IDE中让LLM为一个函数calculate_discount(user_id,item_id)生成单元测试。要想生成有效的测试，LLM除了要知道这个函数的代码，还需要知道下面的相关内容：
（1） user_id对应的数据结构（可能定义在models/user.py中）
（2） item_id对应的数据结构及其价格信息（可能定义在models/item.py中）
（3） 项目中可能存在的特定折扣规则或配置（可能在config/settings.py或数据库中）。
（4） 可能在聊天中提到的“VIP用户有特殊折扣”这样的信息。
在没有MCP的情况下，你要手动输入这些信息，并将其作为塞进一段冗长的Prompt里。如图2-1
 
相比之下，MCP可以提供机制让MCP Host(IDE)能够自动收集这些分散在不同文件甚至历史记录中的信息片段，由MCP Client转递给MCP Server进行整合，再提供给LLM。
2.	上下文传递效率低下
现在假设user.py和item.py文件各自有数千行代码，包含许多依此函数无关的类和方法。如果没有MCP,按照传统的方法，要先找到User和Item类的定义、相关的辅助函数，再再将他们输入到Prompt当中，过程极其繁琐，容易出错。如果使用MCP作为一个方案，那么该方案具备传递符号的引用、传递代码片段、传递差异和传递抽象语法树。通过这些方式，MCP可将原始的，可能冗余的文本信息转化为结构化，与任务紧密相关的精炼信息，提高通信效率，为MCP Server和LLM提供更易于处理的输入。
MCP的产生目的是解决上下文信息碎片化、传递效率低下以及相关性难以把握这三大核心问题，从而让LLM能够更好的理解用户意图和环境，提供高质量的辅助。


2.2.	MCP核心结构
MCP的核心架构是三个协同工作的组件。MCP的生态系统主要由MCP Host、MCP Client和MCP Server核心组件构成。
1.	MCP上下文协议
在MCP还没有出现之前，AI应用依赖于各种方法，例如手动API连接、基于插件的接口和代理框架等，与外部工具交汇。如图所示，这些方法要将每个外部服务与特定的API集成，从而导致复杂性增加和可扩展性受限。 
MCP通过提供标准化的上下文协议来应对相应挑战，从而实现与多个工具的无缝连接和灵活交互。
2.	MCP核心组件：MCP Host 与MCP Client
	MCP Host:
MCP Host是MCP架构的核心容器，是与用户直接交互的前端应用程序或环境，是原始上下文信息的天然来源，最了解用户正在做什么、看到什么，以及应用程序当前状态。可以理解MCP架构当中的“眼睛”和“耳朵”，MCP Host肩负着连接用户意图与MCP的初始桥梁作用。
	MCP Client
MCP Client是一个轻量级的中间件，通常作为插件、扩展或库嵌入MCP Host环境运行，我们可以理解为是AI模型和外部工具之间的“翻译官”，负责把AI的指令转换成工具能理解的请求，在把工具返回的结果整理好送回AI。MCP Client的主要作用在于支持与MCP Server的通信，这对AI项目来说是一个核心部分。
3.	MCP核心组件:MCP Server
MCP Server是MCP架构 “大脑”，处理 Client 协议消息，协调和 LLM 交互，可本地或云端运行，打破数据孤岛。
	操作流程：
接收 Client 传来的 context/update 消息后，整合信息成连贯上下文视图；为代码符号、文档等上下文建索引方便检索；分析上下文相关性，剪枝无关信息适配 LLM Token 限制 。
	提供内容：
Resource：给 Client 各类数据（文件、数据库记录等），用唯一 URI 标识，如 file:///home/user/documents/report.pdf 。
Prompt：定义可复用提示模板 / 工作流，含动态参数、Resource 上下文等，Client 用 prompts/list 发现可用 Prompt ，用 prompts/get 请求使用 。
Tool：Server 暴露的可执行函数，Client 用 tools/list 列可用工具，用 tools/call 调用，能做简单计算或复杂 API 交互 。


2.3.	MCP通信机制与协议
1.	底层通信方式
	标准输入输出（STDIO）：
Client 和 Server 用系统标准输入输出交换数据，适合二者在同一台计算机（如 LLM 本地工具通信） 。
	服务器发送事件（SSE）：
HTTP 标准，支持 Server 向 Client 推数据，实现双向通信，适合跨计算机网络通信场景，Client 也能用 HTTP POST 发数据给 Server ，未来还可集成 WebSocket 。
2.	消息格式、关键命令 / 事件与会话管理
	消息格式：
用 JSON-RPC 2.0 ，消息是 JSON 对象，含 jsonrpc（协议版本 “2.0” ）、id（消息唯一标识，请求消息必需 ）、method（调用方法 / 命令名 ）、params（可选参数 ）、result（响应结果 ）、error（错误详情 ）字段 。
	关键命令 / 事件：
initialize：Client 发此命令初始化和 Server 连接，交换协议版本、功能信息 。
initialized：Client 发通知告知 Server 初始化完成 。
shutdown：Client 发命令请求 Server 关闭连接 。
exit：Server 发通知告知 Client 即将关连接 。
tools/list：Client 查 Server 支持工具列表 。
tools/execute：Client 请求 Server 提供指定工具 。
resources/get：Client 获取指定资源 。
prompts/execute：Client 请求 Server 提供指定提示 。
	会话管理：
从 Client 发 initialize 开始，到发 shutdown 或 Server 发 exit 结束，期间可交换多消息、执行操作，定义了连接建立、消息交换、错误处理、连接关闭的生命周期 。
3.	MCP 交互流程与工作原理
组件协同：
MCP Host、Client、Server 协同，用户给 Client 发提示，Client 分析意图，Server 选工具，调用外部 API 检索处理信息后回应用户 。
